# Ethereus tool-use fine-tune — spec v1

Date: 2026-11-01. Owner: the dispatcher. Goal: a 9B checkpoint that *reaches for* `eth` and `files` when it should, with the circuit untouched and the gates still green.

## 1. The problem, in numbers

- ETH Evals circuit arm: 1 tool call in 105 requests, and that one was a test.
- Smoke test on `q9-store-rv`: base 3/20, with the knowledge snapshot 4/20. The files are loaded; the model does not read them.
- Gate 4 prompt 6: the model wrote calldata by hand instead of calling `run`.

The tools are exact. The model does not use them. This fine-tune changes only that.

## 2. What changes and what does not

| Trained | Frozen |
| --- | --- |
| Qwen's own layers (layers 12–43 of the merged model), LoRA rank 16 on attention + MLP projections | The 11 compiled chip layers, byte for byte |
| — | Embedding rows for chip tokens; `lm_head` rows for chip tokens |
| — | The DeltaNet heads the store uses (the snapshot must load identically after training) |

Assert before and after training: `sha256` of every chip-layer tensor unchanged; gate 2 (`gpucheck --decode`) still 18/18 exact; snapshot `--mode verify` still 136/136.

Base checkpoint: `q9-store-rv` (has both circuits). Output: `q9-store-rv-ft1`.

## 3. Data

Three sources, all synthetic or already captured. No hackathon data yet. Target 3,000–5,000 examples; quality over count.

**A. Tool-call demonstrations (≈2,500).** Generated by a script, `scripts/gen_ft_data.py`, from templates with randomised values. Each example is a full chat: system line (the one the API uses), a user turn, the correct `<tool_call>`, the circuit's exact `<tool_response>` (produced by running the reference machine — never typed), and a final assistant turn that reads the response correctly.

| Family | Count | What it teaches |
| --- | --- | --- |
| selector / encode / decode | 800 | "hash this / encode this" → call `eth`, then copy the hex verbatim |
| u256 arithmetic, wei↔ether, overflow | 400 | arithmetic on big numbers → call `eth u256`, trust the answer |
| create / create2 | 200 | address derivation → tool, not reasoning |
| `run erc20` / `getAmountOut` on the fixture | 400 | "what would this call return" → `run`, then read `return` not `gas` |
| `files get es/<topic>` before Ethereum facts | 600 | questions on gas prices, EIPs, L2 costs, ERC-8004, x402 → read the file first, answer from it, cite it |
| negative examples | 100 | questions that need no tool (general Solidity, history) → answer directly, no call |

Final-turn rule: after a tool response, the assistant restates the result exactly (no stray spaces in hex, no re-deriving), and never re-calls the same tool with the same arguments.

**B. Gate-4 and eval traces that verified (≈100).** The circuit-arm trajectories and gate runs where the model *did* call a tool and the owner mask verified. Few, but real.

**C. ETH Evals knowledge Q&A (≈500).** From the `es/` files: question, `files get` call, the file's content as the tool response, answer grounded in it. Generated from the packed files, not written by hand; checked that every answer string appears in the cited file.

Hold out 10% by family. Also hold out the 20 smoke-test questions entirely — they are the eval, not training data.

## 4. Training

- Script: `research/hidden-reasoning/hcot/train.py` pattern (the author's LoRA setup that freezes the compiled layers). Adapt to the merged model: target modules on Qwen layers only, by name.
- Loss only on assistant tokens the model generates: the `<tool_call>` block and the final answer. **Zero loss on `<tool_response>` tokens** — those are circuit output, not predictions.
- 2 epochs, lr 1e-4, batch 16, max length 4,096, bf16. One pass on the eval VM's GPU; a few hours.
- Merge the LoRA into the Qwen layers at the end; save as a stock checkpoint so `RvChat` loads it unchanged.

## 5. Evaluation (all must pass before the checkpoint is used)

| Check | Pass |
| --- | --- |
| Chip-layer tensors | sha256 identical to `q9-store-rv` |
| Fine-tune gate (Fraser, 2026-11-02, replaces gate 1's cap here) | KL against stock Qwen3.5-9B ≤ 0.05 on generic prompts (`textcheck`), **and** MMLU-500 within 1 point of stock (`scripts/eval_mmlu.py`, or DMind held-out). The 2×6e-4 cap is a merge test, not a fine-tune test; it stays for merges. |
| Gate 2 | 18/18 exact |
| Gate 4 | 6/6 clean, prompt 6 now calls `run` |
| Snapshot verify | 136/136 |
| Held-out tool-call set | ≥ 90% correct tool + arguments; ≥ 95% final answer matches tool response byte-exact |
| Smoke test (20 held-out) | with `--fs` ≥ 12/20 (from 4/20) |
| Ethereus Act test | Ethereus arm ≥ host-ceiling − 1 task |
| ETH Evals Concepts, circuit arm | tool calls > 0 in the run; score ≥ base (a tie is acceptable, a drop is not) |
| Red-flag check | on 50 non-Ethereum prompts, 0 spurious tool calls |

If the fine-tune gate or the red-flag check fails, add or raise the KL-to-stock term (`train_ft.py --kl-weight`), lower the LoRA rank, or drop epoch 2; do not loosen the checks. (Fraser, 2026-11-02: ft1 epoch 1 had KL 0.075 against stock without the term; retraining with it.)

## 6. Deliverables

- `scripts/gen_ft_data.py`, the generated dataset (`data/ft1/*.jsonl`, with a manifest: counts per family, seed, reference-machine firmware hash).
- `scripts/train_ft.py` and the run log with loss curves.
- `dist/q9-store-rv-ft1/` on the box with sha256sums; the eval table above in `docs/finetune-ft1.md`.
- The same eval table for `q9-store-rv` beside it, so the delta is one glance.

## 7. Out of scope

Hackathon data (not collected yet), reasoning improvements, new tools, Kimi, anything that touches the compiled layers. If the model needs to be *smarter* rather than *tool-using*, that is the backbone roadmap, not this.

## 8. External data (survey 2026-11-01)

Nothing on Hugging Face supplies (a) or (b) directly; all training rows are generated. Use these in supporting roles only:

- **Format template:** `SatoHub/sato-mcp-tool-calling` (CC-BY-4.0): copy its `messages`/`tools` structure and its ~17% negative-example ratio; replace its tools with `eth` and `files`.
- **Raw material for tool examples:** real ABIs from `Zellic/smart-contract-fiesta` (or `mwritescode/slither-audited-smart-contracts`, MIT) for the selector / encode / decode / create2 families; answers come from the reference machine, never from the dataset.
- **Second held-out knowledge eval:** `DMindAI/DMind_Benchmark` (CC-BY-4.0), the Security + SmartContract + Infrastructure subsets (~1,000 MCQ). Report base vs ft1 beside the smoke test.
- **Never train on:** `buidlguidl/ethevals-test` (contains solutions), `DMind_Benchmark` (it is the eval).
- Knowledge source text for the `files get` family: the `es/` pack already in the snapshot; for more, ingest `github.com/ethereum/EIPs` (CC0) directly. No HF EIP corpus exists.
